## C01: originales y autorización del ZIP

Se añadió action zip al handler final existente, protegido por su política read y contrato HTTP estricto. Campos únicos: action,workshopId,revisionId,requestId. No rutas, bytes, plan, rol, nombres o actor recibidos del cliente. No SQL nuevo, bucket, Storage público ni archivo ZIP persistido.

El servidor verifica sesión y plan Plus/Full mediante bt_commercial_status, y obtiene el expediente completo autorizado mediante bt_final_archive_document. Conserva owner/admin, RLS y pertenencia de cada referencia. Solo acepta quote/report/handover en su revisión, exactamente tres archivos distintos y hashes distintos. Descarga los originales con finalArchivePorts.download, valida tamaño/envelope/SHA-256 y vuelve a consultar sus referencias. Cotización usa meteredDocument con la misma identidad actor/taller/revisión/UUID que la descarga individual: preview, ZIP y reintento vigente no añaden una operación ni consumos duplicados. Informe y constancia conservan su autorización histórica por servidor; no se les inventa una cuota comercial nueva.

El ZIP se construye en memoria en formato STORE con CRC32, nombres descriptivos sin datos personales y fecha técnica estable. Antes de emitirlo, reconsulta plan, identidad y manifiesto completo; revalida la autorización comercial de la cotización con el mismo UUID y caché canónico. Una reserva inesperadamente nueva en ese punto se rechaza, sin render ni fallback. Si falla cualquier original, la autoridad o el manifiesto, no entrega ZIP parcial. Las copias temporales de los PDF se sobrescriben al salir; un ZIP preparado que no supera la comprobación final también se descarta/sobrescribe. No se regenera ningún PDF para completar un archivo.

Límite agregado:12.000.000 bytes de PDF; ZIP máximo agregado más2048 bytes de envoltura. Cada objeto privado conserva además el límite20.000.000 bytes y se comprueba su tamaño antes de pedir otro arrayBuffer. El presupuesto limita los buffers explícitos; no se presenta como medición/certificación del pico RSS en Edge. Hay copias transitorias de SDK/Blob/Response y se requiere evaluación del runtime antes de despliegue. El parser cliente acepta únicamente nuestra envoltura STORE de tres entradas, sin cifrado, nombres/offsets/CRC/central/EOCD extraños ni bytes añadidos, y vuelve a verificar SHA-256 contra el manifiesto autorizado. No extrae ficheros a disco.

Compatibilidad SDK verificada: FunctionsClient instalado reconoce PDF y application/octet-stream como Blob, pero application/zip como texto. Por ello el endpoint responde application/octet-stream con Content-Disposition attachment y filename.zip. El frontend convierte bytes ya verificados en Blob application/zip. Dos pruebas adicionales conectan el SDK REAL y el repositorio frontend REAL con el handler y PostgreSQL reales, sin una respuesta HTTP ideal que oculte esta diferencia.

El cliente vuelve a comprobar referencias, plan actual, fence y UUID antes de habilitar la descarga. Un cambio de autorización, sesión o taller descarta resultados tardíos y revoca las Blob URLs propias. ZIP no se guarda en estado, sessionStorage o caché; su URL tiene TTL1,5s y participa en invalidación global. Datos de operación persistidos son exclusivamente metadata de reintento.

Una cotización confirmada antes de que falle otro original conserva su consumo autorizado. No se reintegra ni cambia UUID automáticamente: el reintento vigente no consume otra vez; al vencer o revocarse la sesión original se conserva el flujo de renovación explícita de Hardening. Nueva autorización explícita puede usar otro cupo conforme al contrato, no una renovación silenciosa. Bajo Básico, ZIP se rechaza por servidor antes de reservar; no cambia la descarga individual legítima del plan Básico.

## Errores y soluciones verificados

1. El foco inicial se guardaba después de deshabilitar el disparador: regresaba a body. Se capturó antes de la petición y se restauró después del cierre/fullscreen, con aserción de foco exacta.
2. La simulación de error del plugin no produjo un aviso fiable. Se agregó alternativa explícita siempre disponible y se valida como interacción real, sin asumir detección universal del plugin.
3. El selector histórico esperaba el título original del iframe. Se preservó ese contrato accesible mediante frameTitle, sin debilitar la prueba ni ampliar timeouts.
4. Poppler bbox mezcló letras grandes rotadas con rótulos horizontales. Se consultó DTK-ERR-020; adaptación específica verifica primero glifos, diagonal y operadores/alpha, luego conserva todas las aserciones históricas. El primer intento de texto sin raw tampoco unía las letras rotadas; se usa raw para comprobar BORRADOR. No se cambia el PDF para satisfacer la prueba.
5. TypeScript detectó un import no utilizado y tipo implícito en el generador de fixtures; se corrigieron en pruebas. No se instala ni cambia dependencia para ocultarlo.
6. Contrato MIME del SDK: application/zip se decodificaba como texto. Se consultó la versión instalada siguiendo DTK-ERR-014; respuesta binaria octet-stream y pruebas de SDK real. El primer laboratorio HTTP no detectaba ese problema: sus16 PASS no se presentan como prueba del SDK; los dos casos nuevos lo completan.
